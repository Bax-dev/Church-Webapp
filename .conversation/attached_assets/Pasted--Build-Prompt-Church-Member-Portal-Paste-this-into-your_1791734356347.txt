## Role

You are a senior full-stack engineer. Build a production-ready **Church Member Portal** using **Next.js (App Router, TypeScript) for both frontend and backend**, **PostgreSQL** as the database, **Redis** for sessions/tokens/rate limiting/caching, and **JWT** for authentication. Follow the attached PRD as the source of truth.

## Tech Requirements

- Next.js 14+ App Router, TypeScript (strict mode), Route Handlers in `app/api/*`
- PostgreSQL with **Prisma** ORM and migrations
- Redis via `ioredis`
- JWT using the `jose` library (access token 15 min, refresh token 7 days, both in httpOnly Secure SameSite=Lax cookies)
- Passwords hashed with **Argon2id** (`argon2` package)
- Validation with **Zod**, shared between client and server
- Tailwind CSS + shadcn/ui, React Hook Form, TanStack Query
- Email via Nodemailer (SMTP configured through env vars)
- Export with `exceljs` (xlsx), `papaparse` (csv), `pdfkit` (pdf)
- Docker Compose file for local PostgreSQL and Redis

## What to Build

### Roles
`MEMBER` and `SUPER_ADMIN`. Members see and edit only their own data. Super Admin sees and manages everything.

### Member features
1. Signup with: first name, last name, email, phone, password, date of birth, marital status (Single, Married, Widowed, Divorced, Separated), address (line, city, state, country), church department (dropdown), district (dropdown), and a consent checkbox.
2. Email verification before login (token stored hashed in Redis, TTL 24 h).
3. Login, logout, forgot password, reset password (token in Redis, TTL 1 h, single use), change password.
4. Profile page and edit-profile page. Members cannot change `role` or `status`. Changing email requires re-verification.
5. Optional profile photo upload (JPG/PNG, max 2 MB).
6. Account deletion request.

### Super Admin features
1. Dashboard: total members, new this month, counts by department and district, upcoming birthdays (cache stats in Redis for 5 minutes).
2. Members table: server-side pagination, sorting, search (name, email, phone), filters (department, district, marital status, status, birthday month).
3. View, edit, deactivate/reactivate, delete, and manually add members; trigger a password reset email.
4. CRUD for departments and districts (archive instead of hard delete when in use).
5. Export the current filtered list to CSV, Excel, and PDF.
6. Reports: birthdays by month, members by department, members by district, marital status summary.
7. Audit log of every change (actor, target, action, old value, new value, IP, timestamp) with a viewer page.
8. Settings: toggle auto-approve vs manual approval for new signups.
9. Manage other admin accounts.

## Authentication and Security Rules (must follow)

- Access token payload: `sub`, `role`, `jti`. Verify in `middleware.ts` for `/admin/*`, `/dashboard`, `/profile`, and `/api/*` (except public auth routes).
- Store each refresh token's `jti` in Redis as `refresh:{userId}:{jti}` with a 7-day TTL. On `/api/auth/refresh`, validate against Redis and **rotate** the token (delete old, issue new).
- On logout: delete the refresh `jti`, add the access `jti` to `blacklist:{jti}` until expiry, clear cookies. On password change or reset: delete all of that user's refresh keys.
- Redis rate limits: login 5 per 15 min per IP+email with temporary lockout; signup 10 per hour per IP; forgot-password 3 per hour per email.
- Re-check the role inside **every** admin API handler; do not rely on middleware alone.
- `/api/me` must take the user id from the verified JWT only, never from params or body (prevent IDOR).
- Whitelist updatable fields with Zod; strip unknown keys; never accept `role`, `status`, or `emailVerified` from member requests.
- Generic error messages on login and forgot-password to prevent account enumeration.
- Never return or log `passwordHash` or tokens.
- Add security headers (CSP, HSTS, X-Frame-Options, Referrer-Policy) in `next.config.js`, and an origin check on mutating requests.
- Secrets only from environment variables.
